# 口径 A：USRC 漏洞报告

## 漏洞标题

统信 UOS 自带 SQLite 3.39.3 未修复 WAL-reset 缺陷，存在数据库静默损坏风险

## 影响产品

- 产品：统信 UOS 桌面专业版 / 服务器版（含 Deepin 20.x 衍生版本）
- 受影响组件：`libsqlite3-0`（`/usr/lib/aarch64-linux-gnu/libsqlite3.so.0.8.6`）
- 受影响版本：本机 UOS 20（eagle 1070）为 **SQLite 3.39.3**（含 `3.39.3.6-deepin1` 等打包修订版）；
  Deepin 当前打包基线为 **3.46.1**（`3.46.1-8deepin6`）；两者都在受影响区间（3.7.0–3.51.2）
- 已验证架构：**aarch64 / ARM64**（UOS 20 实机）
- 受影响架构：全部架构（纯 C 源码缺陷，与架构无关）
- 修复状态：**未修复**。`debian/patches/` 已有 30 条补丁（含 CVE-2026-11822/11824/119371–119379/
  119591/39113/50812/50813），唯独没有这一条——因为上游这次修复**没有 CVE 编号**

## 漏洞类型

- CWE-662: Improper Synchronization（同步处理不恰当）
- CWE-664: Improper Control of a Resource Through its Lifetime（资源生命周期管理不当）

## 严重程度（建议评估）

**本报告不主张把它定为漏洞。** 它没有 CVE 编号，上游已公开、已修复、已出 backport，
按漏洞流程很可能被判"已知问题、不收取"。

如果贵方仍需要定级，参考事实是：

- 不导致崩溃/提权/远程利用 → 不构成高危
- 上游原文定性为"unlikely to occur in common use"，并称野外发生率"小于等于 SSD 故障或宇宙射线的预期发生率"
- 一旦命中，后果是**已提交事务的数据静默丢失/库损坏**，不报错，发现时不可恢复
- 影响所有以 WAL 模式多连接使用 SQLite 的应用（本机实测 294 个进程链接该库）

因此建议按 **"发行版补丁滞后 / 组件安全基线"** 类缺陷受理，或转交打包维护者。
若判定不属 USRC 范围，请直接转对应入口，我不再重复提交。

## 漏洞描述

SQLite 3.39.3 的 WAL（Write-Ahead Log）实现存在缺陷：
在某些并发读写时序下，WAL 文件被异常重置（WAL-reset），
**已提交的事务对应的数据页会被回滚/丢失，且数据库不报告任何错误**。

由于 SQLite 默认在很多上层框架中被配置为 WAL 模式（移动端、桌面应用、开发工具、
部分系统组件），该缺陷在实际使用中触发条件并不苛刻：只要存在并发读者与写者的交错，
且恰逢 WAL 重置窗口，就可能命中。

上游修复版本：

| 修复版本 | 说明 |
|---|---|
| 3.51.3 | 主线修复（2026-03-13） |
| 3.44.6 | 3.44 分支 backport |
| 3.50.7 | 3.50 分支 backport |

参考：<https://sqlite.org/wal.html#walresetbug>

其它发行版的跟进情况（可作为"该做什么"的参照）：

| 发行版 | 状态 |
|---|---|
| Ubuntu jammy / resolute | 已 backport（LP #2171337） |
| SUSE SLE 12/15、Micro 6.0 | 已升级到 3.51.3 |
| Debian bookworm / trixie | 未合入 |
| 统信 / Deepin 打包 | 未合入 |

## 复现与验证方式

WAL-reset 属时序竞争问题，无法用确定性 SQL 用例稳定复现，
因此**判定依据为版本比对**：

```bash
# 1. 确认当前版本（3.39.x 即为受影响）
sqlite3 --version
python3 -c "import sqlite3; print(sqlite3.sqlite_version)"

# 2. 确认库文件版本
ls -la /usr/lib/aarch64-linux-gnu/libsqlite3.so.0.8.6
dpkg -l libsqlite3-0

# 3. 确认发行版源内无更高版本
apt-cache policy libsqlite3-0

# 4. 观察影响面（本机实测 294 个进程）
sudo lsof 2>/dev/null | grep -c libsqlite3
```

补充说明：我在自编译 3.54.1 后做过并发压力测试（13 线程混合读写、1285 次事务写入），
`PRAGMA integrity_check` 通过、无异常，可作为"新版在 UOS 环境下工作正常"的佐证。

## 建议修复方案

**方案一（推荐）：backport 到当前打包基线**
以最小改动合入上游 WAL-reset 修复，保持 ABI 与功能特性不变
（该库被大量程序依赖，不宜大版本跳跃）。

**这条补丁我已经做好了，可直接交付**：`56-WAL-reset.patch`，适配 3.46.1 基线，
改 `src/wal.c` 两处 + 上游回归用例；在 3.46.1 官方源码上零 reject 应用，
x86_64 编译通过，A/B 回归为 0 errors/7（未打补丁版为 2 errors/7）。
补丁、构建指纹与原始输出见：https://github.com/pzmmy/sqlite-walreset-uos

**方案二：升级到 3.5x 稳定分支**
需完整回归测试，并提供 arm64/x86_64/龙芯/鲲鹏/飞腾等多架构包。

**方案三（临时缓解）：明确告知用户风险**
若短期无法修复，建议在版本说明或安全公告中提示 WAL 模式风险，
并建议关键应用临时切换为 `journal_mode=DELETE`（牺牲并发性能换取安全）。

# 口径 B：论坛/工单 缺陷反馈（更简短，易读）

**标题**：建议尽快修复 UOS 自带 SQLite 3.39.3 的 WAL 数据损坏缺陷

**正文**：

UOS 和 Deepin 目前自带的 SQLite 是 3.39.3，这个版本存在官方已确认的 WAL-reset bug，
在特定并发场景下会导致**数据库内容静默损坏**（不报错、不崩溃，发现时数据已丢）。
SQLite 官方已在 3.44.6 / 3.50.7 / 3.51.3+ 修复。

现状是：

- 软件源里 `libsqlite3-0` 最高只到 `3.39.3.6-deepin1`，属于打包修订，**没有 backport WAL 修复**；
- `pysqlite3-binary` 只提供 x86_64 轮子，**arm64 用户没有现成替代方案**；
- 该库被系统中大量程序依赖（我这台机器实测 294 个进程链接它）。

风险不限于"数据库应用"：浏览器、笔记、聊天记录、开发工具乃至部分系统组件都用 SQLite，
只要程序在 WAL 模式下做并发读写就存在命中可能。

希望官方能：

1. 将 WAL-reset 修复 backport 到现有 3.39.3 包（改动最小、风险可控）；
2. 或升级到 3.5x 稳定分支并提供多架构包；
3. 若短期无法修复，至少在公告中提示 WAL 模式风险及临时规避方式（改用 DELETE 日志模式）。

附件/附链接：我在 UOS arm64 上自编译 3.54.1 做了完整验证（含 10 项功能测试与并发压力测试），
确认新版在本环境工作正常，脚本已开源：https://github.com/pzmmy/sqlite-walreset-uos
可作为 backport 可行性验证的参考。
